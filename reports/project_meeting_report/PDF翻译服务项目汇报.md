# PDF 翻译服务项目汇报

## 一、项目背景

在跨语言资料流转、海外业务协作、供应商文档审核、技术资料归档等场景中，PDF 文档往往是最常见的交付格式。传统机器翻译可以处理纯文本，但面对 PDF 时会遇到几个实际问题：

1. PDF 不是单纯文本文件，很多内容由坐标、字体、图片、表格和扫描图组成。
2. 扫描件、截图型 PDF、合同盖章文件、手册和说明书通常没有可直接提取的文字层。
3. 表格、目录、公式、页眉页脚、侧边栏、图注等结构如果被当成普通段落处理，翻译后版面容易错乱。
4. 企业场景经常需要保留原始排版，方便审核人员对照原文件，不只是得到一份抽取后的译文。
5. 实际部署环境差异较大，有的客户希望完全走云端 API，有的客户出于成本、速度或数据合规考虑，希望 OCR 能力部署在本地或内网服务器。

本项目的目标是提供一套可部署、可调用、可扩展的 PDF 翻译服务：通过统一接口上传文档，后台自动完成 OCR、版面结构解析、翻译、回填渲染和结果下载，并尽量保留原文档视觉结构。



## 二、项目定位

本项目不是简单的“PDF 转文字再翻译”，而是一套面向文档版面还原的翻译流水线。它重点解决的是：在 PDF 原始页面上尽可能保留原布局、原坐标、原视觉层次，将可翻译内容替换为目标语言，并输出可交付的 PDF 或图片结果。

项目对外提供统一的 FastAPI 服务，支持任务式异步处理。用户或上层系统只需要调用 `/tasks` 上传 PDF，再轮询 `/tasks/{task_id}` 查询进度，完成后下载结果文件。

核心价值可以概括为：

1. 支持扫描件和原生文字 PDF 两类主要输入。

2. 支持本地 OCR 和云端 OCR 两种部署路线。

3. 支持 OpenAI 兼容的大模型翻译接口，模型供应商可替换。

4. 支持复杂版面、目录、表格、公式、图片块二次 OCR 等增强处理。

5. 输出纯译文 PDF、双语 PDF、双语对照 CSV，方便审阅和归档。

6. 支持 Docker 部署，适合在云服务器或内网服务器落地。

   

## 三、适用范围

### 3.1 适合处理的文档

项目适合以下类型的文档翻译：

1. 海外供应商手册、设备说明书、产品说明书。

2. 政府、医疗、采购、物流、制造业相关 PDF 材料。

3. 扫描版合同、盖章文件、图片型 PDF。

4. 有较强版面要求的培训材料、操作手册、制度文件。

5. 带表格、目录、列表、页眉页脚、侧边栏、图注的复杂文档。

6. 需要保留原始视觉布局，方便人工复核的资料。

7. 需要批量接入业务系统的 PDF 翻译服务。

   

## 四、整体架构

项目由统一服务层、任务编排层、OCR 层、翻译层、渲染层和产物层组成。

```text
用户 / 前端 / 业务系统
        |
        v
FastAPI 服务
        |
        v
任务队列与任务状态管理
        |
        v
文档分类与引擎路由
        |
        +-----------------------------+
        |                             |
        v                             v
v3 / BabelDOC 路线              RetainPDF / OCR 路线
原生文字层 PDF                  扫描件 / 图片型 PDF / 复杂版面
        |                             |
        v                             v
大模型翻译 API                  OCR + 结构化文档 + 大模型翻译
        |                             |
        +-------------+---------------+
                      |
                      v
             PDF 渲染与结果生成
                      |
                      v
      纯译文 PDF / 双语 PDF / 对照 CSV
```

### 4.1 服务入口

项目使用 FastAPI 对外提供 HTTP 接口，主要能力包括：

1. `POST /tasks`：创建 PDF 翻译任务。
2. `GET /tasks/{task_id}`：查询任务状态和进度。
3. `GET /tasks/{task_id}/result`：下载纯译文、双语 PDF 或双语 CSV。
4. `GET /tasks/{task_id}/bilingual`：任务运行中实时导出已完成部分的双语对照 CSV。
5. `POST /images/translate`：图片翻译任务。
6. `POST /normalize`：PDF 页面标准化。
7. `GET /health`：服务健康检查。

### 4.2 引擎路线

项目内部有两条主要处理路线：

| 路线 | 适用对象 | 特点 |
| --- | --- | --- |
| v3 / BabelDOC | 原生文字层 PDF | 复用已有文字层，速度较快，适合文本型 PDF |
| RetainPDF / OCR | 扫描件、图片型 PDF、复杂版面 | 先 OCR 和版面解析，再按原坐标回填翻译，适合无文字层或复杂文档 |

当前对外使用上，用户可以通过 `text_based` 参数选择：

1. `text_based=true`：优先走原生文字层翻译路线。

2. `text_based=false`：走 OCR 路线，适合扫描件和图片型 PDF。

   

## 五、核心处理流程

完整 PDF 翻译流程如下：

```text
上传 PDF
  |
  v
读取页数并创建任务目录
  |
  v
根据 text_based 和文档特征选择处理路线
  |
  v
OCR / 文字提取 / 版面解析
  |
  v
生成统一中间文档结构 document.v1.json
  |
  v
按页、块、结构角色组织翻译单元
  |
  v
调用 OpenAI 兼容 LLM API 翻译
  |
  v
进行翻译结果校验、术语处理、遗漏恢复
  |
  v
按原页面坐标构建渲染块
  |
  v
使用 Typst / PDF 工具生成译文覆盖层
  |
  v
输出单语 PDF、双语 PDF 和双语对照表
```

这个流程的关键点是“统一中间结构”。不同 OCR provider 返回的数据结构不同，项目会先将其转换为统一的 `document.v1.json`，之后翻译和渲染都基于统一结构运行。这降低了后续扩展 OCR provider 的成本，也避免翻译层直接绑定某个 OCR 厂商的原始 JSON。



## 六、复杂版面处理能力

### 6.1 保留原坐标与版面结构

RetainPDF 路线会读取 OCR 返回的文本块、表格块、图片块、行级坐标和页面尺寸信息。翻译后，系统不是重新生成一篇普通文档，而是将译文放回原页面对应位置。

这样做的好处是：

1. 页面整体结构和原文相似，方便业务人员对照。
2. 标题、正文、侧边栏、页眉页脚等内容可以保留原位置。
3. 扫描件也可以得到接近原版式的译文 PDF。
4. 对供应商手册、操作指南、说明书等材料更友好。

### 6.2 目录处理

目录页通常有几个特殊点：

1. 目录标题可能没有页码。
2. 目录项存在点线连接符。
3. 左侧编号、标题、右侧页码需要分别处理。
4. OCR 或翻译输出可能包含不完全一致的行结构。

项目针对目录页进行了结构化识别和渲染：

1. 将目录项拆分为编号、标题、页码。
2. 翻译标题时保留原页码。
3. 渲染时按源行的 `line_index` 对齐，避免标题和页码错位。
4. 对无页码的目录引导行单独保留，避免类似 “Tabla de contenido” 被丢失。
5. 无页码行按普通文本渲染，不绘制目录点线。

这类处理可以显著提升目录页可读性，避免“目录项整体平移一行”“页码对应错位”等常见问题。

### 6.3 表格处理

表格是 PDF 翻译中最容易出问题的结构之一。项目对表格有两层策略：

1. 默认策略：为了保证页面稳定，表格翻译默认可以关闭，避免复杂表格被错误回填。
2. 启用策略：通过 `enable_table_translation=true` 可以开启表格内容翻译。

当开启表格翻译时，系统会尽量保留表格结构：

1. OCR 层识别表格块或 HTML 表格结构。
2. 翻译层对表格内容进行特殊处理，避免把整张表当作普通段落。
3. 渲染层对 HTML 表格进行解析，按行列、合并单元格、空白行等信息重建表格。
4. 对空表格行保留书写空间，适合表单类文件。
5. 若表格结构异常，会进行降级处理，防止原始 HTML 标签直接泄漏到最终 PDF。

需要说明的是，表格翻译效果高度依赖 OCR 结果。如果 OCR 只返回一个大文本块，而没有表格结构或单元格信息，系统仍可翻译文字，但很难做到精确表格还原。因此在复杂表格项目中，建议优先使用结构化能力更好的 OCR provider，并在上线前用样本文档做回归测试。

### 6.4 图片块与二次 OCR

部分 OCR 服务会把“包含文字的截图区域”识别为一个大图片块，而不是拆成文本块。这样会带来两个问题：

1. 图片里的文字不会进入正常翻译流程。
2. 渲染时可能把整个图片区域覆盖，造成页面大块空白。

项目提供图片块二次 OCR 机制：

1. 对符合条件的图片块进行裁剪。
2. 将裁剪区域生成临时单页 PDF。
3. 再调用 OCR 识别裁剪区域内部文字。
4. 如果二次 OCR 能拆出更细的文本或表格块，就用这些结果替代原大图片块。
5. 对极短文本噪声进行过滤，避免图标、按钮、装饰字符被误识别成正文，例如单字误识别。

相关配置包括：

| 配置项 | 作用 |
| --- | --- |
| `RETAIN_PADDLE_IMAGE_REOCR` | 是否开启图片块二次 OCR |
| `RETAIN_PADDLE_IMAGE_REOCR_MAX_BLOCKS` | 限制每个任务参与二次 OCR 的图片块数量，控制成本和耗时 |
| `RETAIN_PADDLE_IMAGE_REOCR_MIN_AREA_RATIO` | 图片块面积占页面比例超过阈值才考虑二次 OCR |
| `RETAIN_PADDLE_IMAGE_REOCR_MIN_TEXT_CHARS` | 原图片块文本少于阈值时更可能被认为需要二次 OCR |

这套机制适合处理截图式说明、系统界面截图、按钮说明、扫描图局部文字等情况。

### 6.5 公式与 Typst 渲染

项目使用 Typst 作为重要渲染能力之一。对于包含公式、数学符号或特殊排版的文本，系统会做额外防护：

1. 识别文本中的公式片段。

2. 对公式占位符和公式文本进行保护，降低翻译模型误改公式的概率。

3. Typst 编译前进行安全检查和清洗。

4. 编译失败时尝试选择性降级，例如公式简化、局部纯文本化或 LLM 修复。

5. 尽量保证最终 PDF 能生成，而不是因为个别公式导致整本失败。

   

## 七、翻译能力与大模型接入

项目通过 OpenAI 兼容接口调用大模型。只要模型供应商兼容常见 OpenAI API 格式，就可以通过环境变量或请求参数接入。

主要配置：

| 配置项 | 说明 |
| --- | --- |
| `LLM_API_KEY` | 大模型 API Key |
| `LLM_MODEL` | 翻译模型名称 |
| `LLM_BASE_URL` | OpenAI 兼容接口地址 |

项目支持在服务端 `.env` 中配置默认模型，也支持在单次请求中传入：

1. `openai_api_key`
2. `openai_model`
3. `openai_base_url`

这种设计适合多租户或多项目场景。例如服务端可以有默认模型，但某个客户任务也可以临时使用指定模型或指定 API 网关。

### 7.1 翻译策略

翻译层不是简单逐行翻译，而是包含策略判断：

1. 对标题、正文、目录、表格等不同结构使用不同处理方式。
2. 对不应翻译的内容进行跳过或保留。
3. 对必须翻译的内容进行强制翻译校验。
4. 对翻译后仍保留原文的内容进行二次判断和恢复。
5. 对目录、表格等特殊结构增加额外保护。

### 7.2 术语表支持

项目支持上传 CSV 或 XLSX 术语表，至少包含：

| 字段 | 说明 |
| --- | --- |
| `source` | 原文术语 |
| `target` | 目标译法 |
| `src_lng` | 可选，源语言 |
| `tgt_lng` | 可选，目标语言 |
| `level` | 可选，术语级别 |

术语表会按当前任务源语言和目标语言过滤。启用 `glossary_hard=true` 后，命中的术语会通过占位符等方式加强约束，适合企业专有名词、产品名、部门名、系统名等场景。



## 八、本地与云端能力

### 8.1 云端 OCR

云端 OCR 适合快速部署和轻量运维。配置方式：

```env
RETAIN_OCR_PROVIDER=cloud
RETAIN_PADDLE_TOKEN=your_paddle_ocr_token
```

云端 OCR 的优势：

1. 部署简单，不需要本地 GPU。
2. 适合中小规模任务或试点阶段。
3. OCR 能力由云端服务维护，升级成本低。

需要关注：

1. 文档会发送到第三方 OCR 服务，需评估数据合规。
2. 大批量任务可能产生 API 成本。
3. 依赖外部网络稳定性和服务可用性。

### 8.2 本地 OCR

本地 OCR 适合对数据安全、内网部署或成本控制要求更高的场景。项目当前支持通过本地 PaddleX / PaddleOCR-VL 服务接入。

本地 OCR 的优势：

1. 文档可以留在本地或内网环境。
2. 可使用自有 GPU 资源处理大批量任务。
3. 有利于企业私有化部署。
4. OCR 服务可独立扩容和维护。

需要关注：

1. 需要准备 OCR 运行环境，通常包括 GPU、Docker 和模型镜像。
2. 本地 OCR 返回结构质量会直接影响翻译和版面还原效果。

### 8.3 云端 LLM API 与自定义 API 网关

大模型翻译本身也支持灵活接入。`LLM_BASE_URL` 可以指向公有云模型服务，也可以指向企业内部 API 网关。只要接口兼容 OpenAI 请求格式，即可替换不同模型供应商。

这种设计给项目带来的好处：

1. 不绑定单一模型厂商。

2. 可根据语言、成本、速度选择不同模型。

3. 企业可以通过 API 网关做审计、限流、密钥管理和日志留存。

4. 后续可接入私有化大模型或专用翻译模型。

   

## 九、输出结果

项目支持多种交付产物：

| 产物 | 说明 |
| --- | --- |
| 单语译文 PDF | 将译文回填到原页面结构中的 PDF |
| 双语 PDF | 原文与译文左右并排，方便人工审核 |
| 双语 CSV | 原文和译文对照表，适合质检、术语检查和二次处理 |
| 图片译文 PNG | 图片翻译接口输出与原图尺寸对应的译文图 |

双语 CSV 在任务运行中也可以实时获取。对于长文档，审核人员可以先查看已完成部分，不必等整本 PDF 完成。



## 十、接口示例

### 10.1 创建 OCR 翻译任务

```bash
curl -X POST http://localhost:8040/tasks \
  -F "file=@example.pdf" \
  -F "lang_in=es" \
  -F "lang_out=zh" \
  -F "text_based=false" \
  -F "ocr_provider=cloud"
```

### 10.2 创建原生文字层翻译任务

```bash
curl -X POST http://localhost:8040/tasks \
  -F "file=@example.pdf" \
  -F "lang_in=en" \
  -F "lang_out=zh" \
  -F "text_based=true"
```

### 10.3 查询任务进度

```bash
curl http://localhost:8040/tasks/<task_id>
```

### 10.4 下载结果

```bash
curl -L "http://localhost:8040/tasks/<task_id>/result?type=mono" -o translated.pdf
curl -L "http://localhost:8040/tasks/<task_id>/result?type=dual" -o dual.pdf
curl -L "http://localhost:8040/tasks/<task_id>/result?type=bilingual" -o bilingual.csv
```



## 十一、项目优势

### 13.1 对业务方的优势

1. 使用方式简单：上传文档、查询进度、下载结果。
2. 输出结果接近原版式，便于会议展示、业务审核和资料归档。
3. 支持扫描件，不要求原 PDF 有文字层。
4. 支持双语对照，方便人工校验。
5. 支持术语表，便于企业专有词管理。
6. 支持本地部署，适合企业数据安全要求。

### 13.2 对技术方的优势

1. FastAPI 接口清晰，方便前端或业务系统集成。
2. 任务目录结构完整，便于定位问题。
3. OCR、翻译、渲染分层清楚，后续可替换 provider。
4. 使用统一中间文档结构，降低跨 provider 适配成本。
5. 支持 Docker 部署，环境可复制。
6. 进度事件统一落盘，便于前端展示和后台排障。
